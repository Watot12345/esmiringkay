# Emiringkay: Infrastructure

## 1. Environments
| Env | Purpose | Notes |
|---|---|---|
| local | Development | Laravel Sail + Docker, coturn container, Mailpit |
| staging | QA and demos | Mirrors production at small scale, test moderation keys |
| production | Live | Managed data services, backups, monitoring |

## 2. Reference topology (MVP)
- **CDN + WAF**: Cloudflare (DDoS protection, caching, bot rules).
- **App servers**: 2 x VPS or containers running PHP-FPM/Octane + Nginx.
- **Reverb**: 1-2 dedicated instances (WebSocket connections are long-lived and memory-bound).
- **Queue workers**: Horizon on its own instance.
- **Database**: managed PostgreSQL with daily backups and point-in-time recovery.
- **Redis**: managed Redis (separate logical DBs for cache, queue, matching, presence).
- **Object storage**: S3-compatible (avatars, flagged evidence frames).
- **TURN**: coturn on its own public-IP servers close to users (Singapore first for PH/SEA).
- **LiveKit**: added in Phase 3 for Plaza group rooms.

## 3. Hosting options
| Option | Pros | Cons |
|---|---|---|
| Hetzner/DigitalOcean + Laravel Forge | Cheap, simple, fast to ship | Manual scaling |
| AWS (ECS/Fargate, RDS, ElastiCache) | Scales well, rich services | More complex and costly |
| Laravel Cloud | Least ops work | Less control, TURN still external |

Recommended: **Forge + DigitalOcean/Hetzner (Singapore) for MVP**, move heavier components to AWS when traffic justifies it.

## 4. Local setup (docker-compose services)
- `laravel.test` (Sail), `pgsql`, `redis`, `reverb`, `horizon`, `mailpit`, `coturn`.
- `.env` essentials: `APP_URL`, `DB_*`, `REDIS_*`, `REVERB_APP_ID/KEY/SECRET`, `TURN_URL`, `TURN_SECRET`, `MODERATION_API_KEY`, `SMS_PROVIDER_*`, `GOOGLE_CLIENT_ID/SECRET`.

## 5. CI/CD
- GitHub Actions pipeline: lint (Pint, ESLint) -> static analysis (Larastan) -> tests (Pest, Vitest) -> build assets -> deploy.
- Branch flow: feature branches -> PR -> staging auto-deploy -> manual promote to production.
- Zero-downtime deploys with Forge or Envoyer; run migrations with `--force` in a gated step.
- Database migrations must be backward compatible for one release (expand, then contract).

## 6. TURN and WebRTC infrastructure
- Run coturn with TLS (port 443/5349) and time-limited credentials generated by Laravel (HMAC shared secret).
- Plan for 15-25% of sessions relaying; roughly 1-2 Mbps per video relayed leg.
- Monitor allocation counts, bandwidth, and failure rates.
- Add regions as users grow (Singapore, then US-West, EU).

## 7. Observability
- Errors: Sentry.
- Metrics: Laravel Pulse (app), Prometheus + Grafana (Reverb, Redis, coturn, nodes).
- Logs: structured JSON to a log service (Better Stack, Loki, or CloudWatch).
- Uptime and synthetic tests: a bot that performs a match and WebRTC handshake every minute in staging and production.
- Alerts: error spike, queue backlog, matching wait > 20 s, TURN failure rate > 10%.

## 8. Security hardening
- TLS everywhere, HSTS, secure cookies, strict CSP.
- Secrets in the platform secret manager, never in the repo.
- Rate limiting on auth, OTP, matching, and report endpoints.
- WAF rules and bot challenges at signup.
- Principle of least privilege for DB users and cloud roles.
- Regular dependency scans (Dependabot, `composer audit`, `npm audit`).
- Penetration test before public launch.

## 9. Backup and recovery
- Postgres: daily snapshots plus PITR, 14-day retention; restore drill each quarter.
- Redis: treated as ephemeral; matching state rebuilds on restart.
- Object storage: versioning enabled for evidence.
- RPO 15 min, RTO 1 h target.
